Stage 1: BUILD – SecureShop E-Commerce Development

Develop a realistic e-commerce application using Python Flask, SQLite, and modern HTML5/CSS3. Functionalities include user authentication, product catalogue browsing, keyword search, shopping cart management, order placement, customer invoice tracking, and an administrative back-office panel.

2

Stage 2: EXPOSE – Controlled Local Sandbox Deployment

Run the application strictly on local loopback addresses (http://127.0.0.1:8080 or http://localhost:8080). Confirm that all endpoints are operational and strictly isolated from production networks, public cloud infrastructure, and unauthorized third-party targets.

3

Stage 3: SCAN – Automated Dynamic Application Security Testing (DAST)

Configure OWASP ZAP (Zed Attack Proxy) to crawl the application using the Traditional Spider and AJAX Spider. Execute an Active Scan against the mapped routes to identify missing security headers, SQL injection vectors, and configuration vulnerabilities.

4

Stage 4: INVESTIGATE – Root Cause & Contextual Analysis

Critically evaluate every scanner alert instead of blindly accepting automated outputs. Answer the 7 essential analytical questions for each finding: WHAT, WHERE, WHY, IMPACT, EVIDENCE, REMEDIATION, and RETEST. Filter out potential false positives and contextualize findings within SecureShop's architecture.

5

Stage 5: EXPLOIT / VALIDATE SAFELY – Controlled Proof-of-Concept Validation

Manually validate the identified vulnerabilities within the local lab without damaging system integrity:
• A01 (IDOR): Authenticate as user and access /orders/2 to inspect Alice's invoice.
• A03 (SQLi): Input ' OR 1=1 -- in the search bar to demonstrate unescaped SQL execution.
• A05 (Misconfiguration): Trigger /debug/crash-test to observe traceback information leakage.

6

Stage 6: FIX – Implementation of Secure Coding Defenses

Apply robust software security mitigations:
• Parameterize all database queries using prepared statements.
• Implement server-side authorization checks comparing session IDs against database record owners.
• Disable debug mode and inject defensive headers (Content-Security-Policy, X-Frame-Options).
• Upgrade outdated packages in requirements-fixed.txt.

7

Stage 7: RETEST – Verification and Regression Testing

Switch the application into FIXED MODE and repeat the testing procedure:
• Rescan the application with OWASP ZAP to verify alert resolution.
• Re-attempt manual payloads (verify 403 Forbidden on IDOR and 0 results on SQL injection).
• Check logs/security.log to confirm security events were captured accurately.

8

Stage 8: REPORT – Documentation and Evidence Presentation

Compile comprehensive cybersecurity documentation including VULNERABILITY_MATRIX.md, SECURITY_FINDINGS.md, and REMEDIATION.md. Demonstrate a side-by-side comparison of the application's before vs after security posture for college evaluation.
